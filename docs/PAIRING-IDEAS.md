# 配对方式调研：换掉"每次都等 TA 发新码"（2026-10-15）

## 现状痛点

- 配对码 6 位 + TTL（repo 默认 10min，线上 hotfix 30min），**解除配对后关系即失效**，
  想再连必须对方重新报一个码。真实场景：拿旧手机测完想重新配对，只能等女友发新码。
- 码是"一次性关系凭证"，没有"老搭档"概念。

## 微信的做法拆解（为什么不能照抄）

| 玩法 | 背后机制 | 对我们的适用性 |
|---|---|---|
| 面对面建群 | 同一地点(LBS) + 同一时间窗 + 4 位数字汇合；靠"附近没人输入同组合"防撞车 | 用户密度低时反而安全：全平台只有他俩，撞车概率≈0。但需要同地点，异地用不上 |
| 摇一摇·人 | 同时摇 + 地理邻近 + 服务端时间桶撮合陌生人 | 陌生人撮合不是我们要的；"情侣定向版"更有意思（见方案 C） |
| 扫一扫 | 二维码 = 带外传输配对码，免手输 | 同场景合房有用；异地没意义 |

## 候选方案

### A. 老搭档一键复配（推荐先做，解决 90% 痛点）

服务端记录"历史配对关系"（deviceIdA–deviceIdB，脱敏存储、30 天过期自动删）。
解除配对后主页出现「找回 TA」：发起 → 对方收到确认弹窗 → 点同意即重新绑定。
- 优点：不发明新输入、不靠地理位置；"我再找到你了"符合产品气质；协议增量小
  （新增 `pair.recall` / `pair.recall_ask` / `pair.recall_ok` 三类消息即可）。
- 风险：历史关系是敏感数据，必须限定"只有对方设备能发起召回+必须人工确认"，
  防被陌生人枚举 deviceId 骚扰（deviceId 不是秘密！必须双向确认 + 冷却时间）。

### B. 配对码免死灰：同码可重复进入

线上 TTL 30min、enter 上限 10 已够宽松；真正断点是"解绑即作废"。B 单独做意义小，
并入 A 的落地里顺手检查即可。

### C. 千里同步·摇一摇复配（浪漫玩法，二期）

双方都在主页 3 秒内摇动手机 → 服务端把两次摇动撮合成"本次复配令牌" → 直接进 A 的确认流程。
本质 = A 的触发器换成摇一摇（时间窗口 ±3s，只与"历史搭档"撮合，绝不与陌生人匹配），
所以没有用户量要求，也不怕别人摇：他不在你俩的历史关系里。
- 传感器数据已有（ShakeDetector 已用于涂鸦入口），客户端成本低。
- 服务端：一个按 deviceId 限频的 rendezvous 小队列（内存态即可，重启丢无所谓）。

### D. 二维码 / NFC

同屏合房才划算；跨机型兼容坑多（Android 7 的 NFC/相机栈、MLKit 体积 +2MB）。暂缓。

## 建议路线

1. **A 先落地**（服务端历史关系表 + 双端 UI + 协议三条消息），痛点当场消失。
2. **C 跟进**（在 A 之上换触发方式，产品记忆点）。
3. 服务器属于高风险区：上线前须人工比对线上 env/常量，改动与部署均需明确确认（AGENTS）。

*（仅调研提案，未动任何代码/服务器。）*
