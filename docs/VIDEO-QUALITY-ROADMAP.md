# Soul2Soul 屏幕共享与远程操作质量改进路线图

版本：v1.0

日期：2026-10-26

适用基线：App `0.2.66`，当前工作树（提交前）

状态：第二阶段部分代码已落地；硬件/功耗/画质结论仍待真机，不得视为商业级达标

## 0. 这份文档要解决什么问题

Soul2Soul 的目标不是“把码率调大”，而是在情侣陪伴场景下，同时做到：

1. 看屏幕时文字清楚、运动画面连续、画面延迟低；
2. 弱网时优先保住语音和操作反馈，而不是整通会话失效；
3. 远程协助时只影响被控手机，不误触本机；
4. 长时间共享不会因为编码、温升、后台策略或音频路由逐渐恶化；
5. 在相同设备、相同网络、相同内容下，核心体验指标达到或超过腾讯会议、UU 远程等同类工具的实测结果。

最后一条必须通过同条件 A/B 测试证明，不能仅凭代码审查、模拟器截图或主观印象宣称完成。

本文将“超过”定义为可核验的目标：在指定测试矩阵内，Soul2Soul 的关键指标至少不低于基准工具；对情侣场景最重要的指标（首帧、冻结、文字可读性、控制反馈、语音连续性）目标比基准好 10%，或在基准工具无法提供等价能力时达到本文的绝对门槛。

## 1. 当前基线：已经有什么，缺什么

### 1.1 已实现的媒体链路

当前版本使用 Android `MediaProjection` + libwebrtc：

- 采集长边档位：`960 / 1280 / 1600 / 1920`；新会话默认 `1920`；
- 最大采集帧率：`30 FPS`；
- 应用层传输预算上限：`1.8 / 2.5 / 3.5 / 3.5 Mbps`；HD 档暂以约 `3.5 Mbps` 控制总流量，真实效果仍需 A/B 校准；
- 屏幕内容源以 `isScreencast=true` 创建；
- 建会前探测硬件编码器能力，优先实际可用的硬件 VP9/H.264/VP8，失败仍回退 WebRTC 软件编码；offer 只提前硬件能力对应的首选 codec；
- WebRTC 统计每 2 秒采样一次，约每 10 秒输出一次 QoS，并从主 outbound 的 `bytesSent` 计算实际发送码率；
- RTT、丢包、可用带宽和帧率驱动画质降级与恢复；
- Android 14 以上不重复使用 `MediaProjection` token，通过 `VideoSource.adaptOutputFormat` 调整输出尺寸/帧率；Android 13 及以下复用同一采集器的 `changeCaptureFormat`；
- 稳定带宽下预算最多使用估计可用上行的约 85%，更新至少间隔 6 秒；静态/无真实统计时不因瞬时估计或缺失 `bytesSent` 盲目改预算；
- 低活动连续三个窗口后目标降为 `8 FPS`，每 8 秒短暂探测 `30 FPS`；网络/编码器受限和远控期间强制保持活动帧率；
- 远程操控期间临时降低到 960 长边并优先保持帧率；
- 媒体优先点对点，无法打洞时使用 TURN；
- 语音与控制数据通道独立于屏幕视频。

实现位置主要在：

- [WebRtcClient.kt](/home/lenovo/ai/soul2soul/app/app/src/main/java/com/soul2soul/app/webrtc/WebRtcClient.kt)
- [NETWORK-QUALITY.md](/home/lenovo/ai/soul2soul/docs/NETWORK-QUALITY.md)

### 1.2 当前能力的客观边界

当前版本不能直接宣称已经和商业工具打平，原因如下：

| 维度 | 当前状态 | 影响 |
|---|---|---|
| 编码器选择 | 已有硬件能力探测、硬件首选和回退；真实 `ENC codec/impl` 设备矩阵仍缺 | 未取得厂商稳定性、温升和耗电证据前不能宣称硬编覆盖率 |
| 档位 | 默认长边 1920，HD 传输预算暂封顶约 3.5 Mbps，最高 30 FPS | 低带宽下以总流量稳定为先，细字清晰度是否优于旧版必须实测 |
| Android 14+ 调档 | 已通过 `adaptOutputFormat` 调整编码输出，不重启投影；旧机型走同一采集器格式切换 | 真实设备连续切档、投影授权和画面连续性仍待验证 |
| 自适应反应时间 | 质量档连续 3 个异常窗口后降档，连续 10 个稳定窗口后恢复；预算至少 6 秒才更新 | 网络突变时仍可能先卡顿；阈值需按真机/竞品 A/B 校准 |
| 中继能力 | 主要依赖单个 TURN 路径，没有专门的媒体转发层 | 跨运营商、NAT 严格或中继拥塞时，质量和延迟受服务器位置影响 |
| 控制模式 | 有意降到 960 并保帧率 | 远程操作跟手性优先，但画面清晰度不能与专业远控同时保证 |
| 证据 | T0–T3 已通过；T4 双真机画质 A/B 尚未完成 | 没有资格声称 MIUI/HyperOS、弱网、温升和听感已达标 |

### 1.3 不能用来冒充质量证明的证据

- JVM 测试只能证明纯逻辑，不证明厂商编码器和实际手感；
- 双模拟器的媒体帧率和网络路径不代表真机，现有测量文档已经记录模拟器约 `0.5 FPS` 的量程限制；
- `PASS(模)` 只证明通路证据；
- T4 `SKIP` 不等于真机通过；
- 单次看到画面清楚，不能证明 30 分钟共享后的稳定性。

真机质量验证必须继续维护 [VALIDATION-TODO.md](/home/lenovo/ai/soul2soul/docs/VALIDATION-TODO.md) 和 [AUDIT-MATRIX.md](/home/lenovo/ai/soul2soul/docs/AUDIT-MATRIX.md)。

## 2. 目标：把“好用”变成可验收的 SLO

目标分三层：绝对底线、发布门槛、超过基准的竞争目标。没有实际读数的目标保持为目标，不写成现状。

### 2.1 视频质量目标

#### 稳定 P2P（同城 Wi-Fi 或良好 5G）

- 首帧时间：P50 ≤ 1.2 秒，P95 ≤ 2.5 秒；
- 稳态接收帧率：P50 ≥ 29 FPS，P95 ≥ 26 FPS；
- 画面冻结：每 10 分钟有效冻结时间占比 ≤ 0.5%；单次非设计性冻结 P95 ≤ 300 ms；
- 端到端画面延迟：P50 ≤ 180 ms，P95 ≤ 300 ms；
- 文字可读性：标准测试页面的关键小字可读率 ≥ 95%；
- 画面恢复：网络恢复后 P95 ≤ 2 秒恢复到可读状态，P95 ≤ 5 秒恢复到目标档位；
- 不因质量调节重启整通会话，不因调档触发 `MediaProjection` 撤销。

#### TURN 中继或普通移动网络

- 首帧时间：P95 ≤ 4 秒；
- 稳态接收帧率：P50 ≥ 24 FPS；
- 端到端画面延迟：P95 ≤ 500 ms；
- 音频优先：视频降级不能导致语音连续性下降；
- 断网 5 秒后恢复：会话无需手动重拨，媒体和控制通道按设计恢复；
- 中继路径连续 30 分钟不出现因服务器排队造成的持续质量恶化。

#### 不同内容的目标

| 内容类型 | 主要目标 | 不能接受的现象 |
|---|---|---|
| 设置页、聊天、照片 | 文字稳定可读，静态画面不产生明显色块 | 字体糊成块、频繁关键帧闪烁 |
| 普通小游戏 | 画面连续，触摸反馈可跟随 | 滑动时连续丢帧、操作后画面超过 500 ms 才更新 |
| 快速滚动/动画 | 优先保持 25–30 FPS，允许短暂降清晰度 | 画面降到个位数 FPS 后仍不自适应 |
| MOBA/高速游戏 | 明确提示“非竞技级远控”，尽量保持可观察性 | 把当前能力宣传成竞技游戏级远控 |

### 2.2 远程操控目标

- 控制消息不与视频大帧互相阻塞；
- 点击/滑动注入延迟：P2P P95 ≤ 150 ms，TURN P95 ≤ 300 ms；
- 从触点到远端画面反馈：P2P P95 ≤ 350 ms；
- 坐标误差：画面内部归一化误差 ≤ 1.5% 屏幕宽度；
- 边缘手势必须明确归属：远程操作期间，观看端右滑不应退出本地 App；
- 权限收回、锁屏、转屏、Activity 重建后，控制授权必须自动失效或可恢复，不能默默落到本机；
- 控制模式退出后，视频档位和用户选择必须恢复，不能永久锁在 960。

### 2.3 语音和设备内录目标

视频质量不能以牺牲语音为代价：

- 双向语音端到端延迟：稳定网络 P95 ≤ 300 ms；
- 音频 RTP 丢包、隐藏时长、AudioTrack 错误必须可观测；
- 发现视频拥塞时，先保留语音和控制通道；
- 设备内录音频与语音同时播放时，不出现持续回声、爆音或 1 秒以上错位；
- `ERROR_DEAD_OBJECT`、路由切换和厂商 Audio HAL 错误必须有恢复或明确提示。

### 2.4 性能和耗电目标

在正式确定绝对电量门槛前，先用同一设备建立基线。暂定发布目标：

- 30 分钟 1600/30 FPS 共享不因温升进入持续降频；
- 编码线程 CPU 占用 P95 ≤ 设备总 CPU 的 25%（低端设备单独标记）；
- 共享 30 分钟温升 ≤ 8°C，超过时自动降低档位并提示；
- 与同条件基准工具相比，电量消耗不高于 1.25 倍；优化完成后目标降到 1.0 倍以内；
- 待机耗电继续遵守 PRD 的 `<2%/小时`，不能用共享态数据掩盖待机回归。

## 3. 目标架构：从“单路视频”升级为“内容自适应媒体管线”

### 3.1 编码器策略：硬件优先、能力探测、可回退

当前固定偏好 VP9 不足以覆盖国产 Android 设备。改造目标：

1. 建会前枚举本机真实可用的编码器：编码器名称、硬件/软件、支持的 profile、最大分辨率、最大帧率和异常黑名单；
2. 优先选择稳定硬件路径，而不是盲目选择理论压缩率最高的编码器；
3. 建立按设备/ROM 的策略表：
   - 硬件 H.264 稳定：优先 H.264；
   - 硬件 VP9 稳定且文字质量更好：优先 VP9；
   - AV1/HEVC 只有发送端和接收端都明确支持且实测收益成立时启用；
   - 编码器异常、首帧超时、连续 `avgEncodeMs` 过高时，自动切换到安全回退档；
4. 不再只靠手写 SDP 字符串调换载荷顺序。优先使用 libwebrtc 的 codec preference API；没有 API 时才保留经过单测和互通测试的 SDP 变换；
5. 记录实际 `encoderImplementation`、`decoderImplementation`、编码耗时和质量限制原因，按设备统计而不是凭型号猜测。

相关改动候选：`WebRtcClient` 的 `PeerConnectionFactory` 创建、offer codec preference、QoS 采样；新增 `VideoCodecCapability`、`VideoCodecSelector` 纯逻辑类。

### 3.2 采集与编码分离：避免 Android 14+ 重启投影

采集分辨率和编码输出分辨率必须分开：

- `MediaProjection` 只创建一次稳定的最大安全采集尺寸；
- 通过 `RtpEncodingParameters.scaleResolutionDownBy`、编码器 scale 或等价的 WebRTC API 改变输出档位；
- 码率、帧率、缩放比例分别由策略控制；
- Android 14+ 禁止重复使用旧 token 的守卫必须保留；
- 只有全新用户授权才允许重新创建投影；
- 采集失败时保活语音和控制通道，显示“画面暂停，点击重新授权”，不能整通电话静默退出。

如果当前 libwebrtc 版本不支持安全的动态缩放，先升级依赖并写兼容探测；不能为了“调档速度”直接恢复 `stopCapture()` + `startCapture()`。

### 3.3 统一的视频档位模型

将现在的“长边”概念扩展为完整 profile。初始建议如下，实际值必须由 A/B 测试校准：

| 档位 | 输出目标 | 帧率 | 目标码率 | 适用场景 |
|---|---:|---:|---:|---|
| Saver | 540–720p 等效 | 20–24 | 0.8–1.5 Mbps | 弱网、后台、低端机 |
| Smooth | 720p 等效 | 30 | 1.5–2.5 Mbps | 操控、普通移动网络 |
| Standard | 900p/1600 长边 | 30 | 2.5–4.0 Mbps | 默认共享 |
| HD | 1080p/1920 长边 | 30 | 4.5–7.0 Mbps | Wi-Fi、文字和照片 |
| Detail | 1080p 高码率 | 30 | 6.0–10 Mbps | 短时看细字，不建议长时间默认 |

档位不能简单绑定固定码率。还要根据屏幕比例、内容运动量、编码器能力、温度、上行带宽和接收端解码能力决定实际值。

### 3.4 自适应控制器：快降、慢升、可解释

改造为独立的 `AdaptiveVideoController`，输入和输出都可单测：

输入：

- RTT、RTT 抖动、发送/接收丢包；
- 可用上行带宽和实际发送码率；
- 编码耗时、CPU、温度、帧率；
- 发送端与接收端的冻结比例；
- 当前 ICE 路径（host/srflx/relay）；
- 当前用户意图（清晰/流畅/省流量/操控）；
- 音频健康状态。

输出：

- 目标 profile；
- 目标码率、最大帧率、缩放比例；
- 是否请求关键帧；
- 是否暂时冻结画质恢复；
- 面向用户的可解释状态（“网络较慢，已优先保证语音”）。

建议策略：

1. 网络恶化时 1–2 个采样窗口内先降码率或帧率；
2. 连续确认恶化后再降分辨率，避免一次尖峰造成明显跳档；
3. 恢复时先恢复帧率，再恢复码率，最后恢复分辨率；
4. 使用滞回、最小停留时间和冷却时间，避免档位来回抖动；
5. 带宽估计未稳定时不因默认初值降档；
6. 音频丢包或隐藏时长恶化时，视频先让出带宽；
7. 温度持续升高时，主动降级并记录原因 `thermal`，不要把热降频误判为网络差；
8. 任何自动调整都记录“原因、旧档、新档、触发指标、持续时间”。

当前 `VideoQualityPolicy` 的降级阈值和滞回逻辑可以复用，但应从“4 个长边常量”升级为 profile 决策。

### 3.5 网络和中继

#### P2P

- 保留 ICE continual gathering 和现有重连预算；
- 记录每一轮选中的候选对，不把 `unknown` 当作直连；
- Wi-Fi/蜂窝切换时优先无缝迁移，不立即拆会话；
- 对短暂断网做媒体和信令分离判断，避免信令断导致健康媒体被提前拆掉。

#### TURN

- 至少部署两个地域或两个出口的 TURN 候选；
- 对移动用户按延迟、丢包和负载选择，而不是固定一个主机；
- 支持 UDP 优先、TCP/TLS fallback；
- 记录 TURN 分配成功率、relay RTT、出口带宽和每会话成本；
- 服务器拥塞时优先保护语音，不要让视频占满中继出口。

#### 是否引入 SFU

两人通话不应为了架构漂亮立刻引入 SFU。只有在以下条件成立时才做：

- TURN 中继成本和质量已经成为主要瓶颈；
- 需要服务端统一转发、录制（若未来产品明确允许）或多端观看；
- 通过压测证明 SFU 能降低移动端 CPU/上行成本；
- 有明确的端到端加密和隐私边界设计。

第一阶段优先把 TURN 做成高质量中继，避免在 P2P 尚未稳定时引入新的媒体故障面。

### 3.6 接收端渲染

- 全程使用硬件解码和 Surface 输出，避免把视频帧转 Bitmap；
- 复用 Surface，避免转屏、PiP、锁屏重建时丢掉渲染链；
- 采集端上报真实帧尺寸，观看端按 aspect-fit 渲染；
- 画面内容矩形、触点归一化坐标和系统手势区使用同一个几何真值；
- 当解码跟不上时丢弃过期视频帧，不阻塞音频和控制数据；
- 关键帧恢复后记录首帧耗时，区分“媒体没帧”和“有帧但 Surface 没显示”。

### 3.7 远程控制通道

远程控制必须是独立的低延迟系统，而不是“把手势塞进视频流程”：

- 控制 DataChannel 使用低队头阻塞策略；
- 每个手势带唯一 ID、首指 ID、序号、发送时间和归一化坐标；
- 远端按首指 ID 串行注入，忽略次指结束污染；
- 控制消息设置最大在途数量和过期时间，过期手势直接丢弃；
- 远程操作状态和本地 Activity 导航状态隔离；
- 控制授权默认关闭、单次会话有效、锁屏/转屏/权限收回自动撤销；
- 控制模式使用 Smooth profile，但在网络允许时可以逐步提高分辨率，不得硬编码永久 960；
- 观看端显示“正在控制对方手机”，并提供一键收回和紧急停止。

## 4. 音频优先与视频协同

视频质量提升不能重新引入此前的短促杂音、回声和内录故障。

### 4.1 带宽优先级

建议优先级固定为：

1. 双向语音；
2. 控制事件和安全状态；
3. 设备内录音频（开启时）；
4. 视频关键帧；
5. 普通视频帧；
6. 诊断和非关键标注。

当 `audioConcealedMs`、音频丢包或播放错误恶化时，视频控制器必须立即让出带宽，并在日志中说明原因。

### 4.2 音画同步

- 设备内录音频使用有界播放缓冲；
- 视频关键帧和音频时间戳都记录单调时钟，不使用设备墙钟相减；
- 迟到的内录帧丢弃，不追赶旧声音；
- 音频路由切换时不重建整个视频会话；
- `ERROR_DEAD_OBJECT`、decoder error、AudioTrack 部分写必须进入同一套恢复状态机。

## 5. 测量与 A/B 基准体系

### 5.1 测试对象

至少建立以下设备池，每个组合至少跑三轮：

| 类别 | 设备样本 |
|---|---|
| 小米/HyperOS | 用户实际使用的 MI17、另一台 HyperOS 中端机 |
| 小米/MIUI | MIUI 真机，覆盖 Android 12/13 或现存用户版本 |
| 非小米 | 一台 Pixel/原生 Android、一台 Samsung 或同等级设备 |
| 低端/旧系统 | Android 7–10 的最低支持设备，单独验证降级和稳定性 |

每轮固定记录型号、Android/ROM、温度、电量、亮度、网络、是否 TURN、App 版本和 commit。

### 5.2 对比工具和内容

同一对设备、同一网络、同一屏幕内容，分别运行：

- Soul2Soul 当前版本；
- Soul2Soul 改进版本；
- 腾讯会议屏幕共享；
- UU远程或用户可获得的同类远控工具。

测试内容至少包含：

1. 静态文字测试页：小字体、长文本、深浅背景；
2. 照片和渐变图：观察色块、细节和关键帧；
3. 普通小游戏：连续点击、拖动、滚动；
4. 快速动画和视频：观察运动画面；
5. 远程控制任务：点击、短滑、长滑、边缘返回手势；
6. 锁屏、转屏、PiP、切 Wi-Fi/蜂窝、短断网和后台恢复。

### 5.3 网络矩阵

受控网络测试至少包含：

| 场景 | RTT | 丢包 | 可用带宽 |
|---|---:|---:|---:|
| 同网理想 | 10–30 ms | 0% | ≥20 Mbps |
| 普通 Wi-Fi | 30–80 ms | ≤1% | 5–20 Mbps |
| 移动网络 | 60–150 ms | 1–3% | 2–10 Mbps |
| 弱网 | 150–250 ms | 3–5% | 1–3 Mbps |
| 极限容错 | 250–400 ms | 5–10% | 0.5–2 Mbps |
| TURN 中继 | 按真实地域测量 | 按真实链路 | 按出口负载 |

不要用双模拟器回环结果代替真机网络结论；模拟器只负责信令、协议和结构性回归。

### 5.4 必须采集的指标

每 2 秒采样，事件发生时额外采样：

- 实际编码器/解码器名称与硬件/软件标识；
- 真实发送/接收分辨率；
- 发送/接收 FPS；
- 实际码率、目标码率、QP（若平台提供）；
- 编码耗时、解码耗时、CPU、温度；
- RTT、RTT 抖动、丢包、NACK/PLI/FIR、可用带宽；
- 首帧时间、关键帧恢复时间、冻结次数和冻结时长；
- audio loss、jitter、concealed duration、AudioTrack 错误；
- ICE path、TURN 节点和重连次数；
- 电量、亮屏状态、前后台状态。

日志必须遵守 [DIAG-READINGS.md](/home/lenovo/ai/soul2soul/docs/DIAG-READINGS.md) 的口径，不上传屏幕内容、SDP 正文、ICE 正文、文本或坐标。

### 5.5 主观评价

客观指标不足以证明“手感”。每轮再做双盲主观评分：

- 清晰度：1–5 分；
- 运动连续性：1–5 分；
- 画面延迟：1–5 分；
- 语音连续性：1–5 分；
- 操作跟手：1–5 分；
- 发热和耗电可接受度：1–5 分。

评分者不知道当前正在用哪个工具，避免“品牌预期”污染结果。

## 6. 分阶段实施计划

每个阶段都必须有代码、测试、审计矩阵和真机证据，不能只完成代码就宣称体验升级。

### Phase 0：建立可比较基线

目标：先知道现在到底有多好。

- 固化 `S2S_QOS` 和会话级媒体指标格式；
- 增加首帧、冻结、关键帧恢复、编码器实现和温度读数；
- 为测试内容制作固定的静态页、运动页和触控页；
- 完成 Soul2Soul/腾讯会议/UU远程同条件三轮 A/B；
- 建立设备、网络、版本和电量记录模板；
- 将当前结果写进 `docs/VALIDATION-TODO.md`，没有读数的格子继续保持 `⬜`。

完成标准：能给出每个设备/网络组合的 P50/P95，而不是一句“感觉比较糊”。

### Phase 1：硬件编码和 profile 系统

目标：消除软编和固定长边带来的性能天花板。

- 新增编码器能力探测与黑名单；
- 实现 H.264/VP9 硬件优先选择和安全回退；
- 将 `VideoQualityPolicy` 改为完整 profile；
- 使用正式 codec preference API，保留老版本 SDP 兼容；
- 对 Android 7、MIUI、HyperOS 分别记录编码器实际选择；
- 加入 `VideoCodecSelectorTest`、`VideoProfilePolicyTest`、旧客户端 SDP 互通测试。

完成标准：目标设备上硬编比例、编码耗时、帧率和温升不劣于当前版本；任何厂商编码器崩溃都能回退且会话不静默死亡。

### Phase 2：Android 14+ 无重启动态调档

目标：弱网下降级不撤销录屏授权，不用高分辨率采集硬压成糊图。

- 升级或扩展 libwebrtc，使编码输出缩放不依赖重启投影；
- 加入 API 能力探测和 `CaptureScaleGuardTest`；
- 档位切换期间保持音频、控制和数据通道；
- 自动调档要有冷却时间、关键帧请求和恢复确认；
- 记录真实 capture size 与 encoded size，避免日志把两者混为一谈。

完成标准：Android 14+ 连续切换三个档位 30 次无 `projection_revoked`、无会话中断；网络恶化后 2 秒内开始有效降级。

### Phase 3：拥塞控制和 TURN 质量

目标：把“直连很好、中继很差”变成可控差异。

- 重新校准 GCC/带宽估计与应用层策略的边界；
- 增加音频优先的带宽预算；
- 关键帧、NACK、PLI/FIR 和恢复路径做设备实测；
- 部署多 TURN 节点，记录节点健康和成本；
- 增加网络切换、NAT 类型、短断网和中继拥塞测试；
- 评估是否需要 SFU，但不在缺少基线前直接替换 P2P。

完成标准：网络矩阵中不因视频拥塞拖垮语音；切网后会话按 SLO 恢复；TURN P95 延迟和冻结率达到发布门槛。

### Phase 4：远程控制和渲染闭环

目标：在不牺牲隐私和本机安全的前提下，达到专业远控的可用手感。

- 控制通道、视频通道、语音通道明确隔离和限流；
- 引入控制事件到画面反馈的端到端 trace ID；
- 加入过期手势丢弃、队列上限和紧急停止；
- 完成不同分辨率、刘海、导航栏、手势导航和转屏的坐标校准；
- 使用硬件 Surface 渲染，验证 Surface 重建不丢帧；
- 控制期间根据真实网络逐步恢复清晰度，不把 960 永久写死。

完成标准：V-01 双真机每个方向至少三轮，坐标误差、边缘手势、本地 App 不误退、权限收回和恢复全部有读数。

### Phase 5：热管理、电量和发布门禁

目标：30 分钟以上共享仍然稳定。

- 监控温度和热状态，必要时以“温度”而非“网络”作为降级原因；
- 建立低端设备安全档；
- 共享 10/20/30 分钟性能曲线；
- 与竞品在同设备、同亮度、同内容下做电量 A/B；
- 版本灰度开启新 codec/profile；
- 出现编码器崩溃、音频错误、温升超阈值时远程关闭新策略。

完成标准：`bash scripts/test.sh` T0–T3 全绿，T4 有明确 PASS 或诚实 SKIP；发布说明包含真实设备、真实网络和未完成格子。

## 7. 测试与 harness 改造清单

### 7.1 JVM 纯逻辑测试

新增或扩展：

- `VideoCodecSelectorTest`：能力排序、硬件优先、厂商黑名单、回退；
- `VideoProfilePolicyTest`：内容类型、网络、温度、音频优先级和用户意图；
- `AdaptiveVideoControllerTest`：快降慢升、滞回、冷却、未知指标；
- `CaptureScalePolicyTest`：API 级别、缩放和投影 token 约束；
- `QualityStatsWindowTest`：累计计数、缺失字段、回绕和窗口边界；
- `ControlGestureStateTest`：首指 ID、次指结束、CANCEL、过期和队列上限；
- `ThermalDegradePolicyTest`：温度降级不能伪装成网络降级；
- `AudioVideoPriorityTest`：音频恶化时视频让出带宽。

每个纯逻辑修复都要验证“抽掉修复后用例变红”。

### 7.2 T0 静态守卫

应锁住以下不变量：

- Android 14+ 质量切换不能调用旧投影重复启动；
- codec preference 不能退回未经测试的裸 SDP 拼接；
- 控制模式必须有进入、收回、锁屏、转屏和会话结束出口；
- 音频优先路径不能被视频背压阻塞；
- 所有新 QoS 字段必须遵守日志长度、白名单和隐私边界；
- profile 档位表、码率表和 UI 文案不能出现互相矛盾的常量。

### 7.3 T4 真机脚本

新增场景：

- `quality-baseline`：固定内容、固定网络、连续 30 分钟；
- `quality-ab`：同设备轮流运行四个工具；
- `quality-network`：带宽、延迟、丢包阶梯；
- `quality-thermal`：温度、电量和降级轨迹；
- `control-edge`：边缘返回手势和本地 App 隔离；
- `capture-scale`：Android 14+ 连续调档和撤销授权恢复；
- `codec-fallback`：模拟编码器失败或能力缺失；
- `audio-priority`：视频拥塞期间语音和内录不被拖垮。

T4 不具备设备时必须 `SKIP`，不能把脚本跑通当成质量通过。

## 8. 发布、灰度和回滚

### 8.1 Feature flags

所有高风险策略都必须可关闭：

- `video_hardware_codec_v2`；
- `video_dynamic_scale_v2`；
- `video_adaptive_controller_v2`；
- `video_turn_region_select_v2`；
- `remote_control_smooth_profile_v2`；
- `audio_priority_scheduler_v2`。

默认策略要能回退到当前稳定版本。服务端下发的策略不能绕过客户端安全上限，也不能把敏感内容写入诊断日志。

### 8.2 回滚条件

出现任一情况立即关闭对应 flag：

- 会话建立成功率下降超过 1 个百分点；
- Android 14+ `projection_revoked` 或录屏重启异常增加；
- 任何目标设备出现编码器 native crash；
- 语音 `audioConcealedMs` 或主观杂音显著恶化；
- 远程控制出现本机误触、错行或无法收回授权；
- 温度或电量相对基线恶化超过 25%；
- TURN 成本或出口带宽超过预算。

### 8.3 版本兼容

- 新旧客户端必须能协商到共同 codec；
- 新字段必须可选，旧客户端忽略未知字段；
- 新 profile 没有对端确认时退回 Standard；
- 不因为远端旧版本不支持高清而关闭语音或基础屏幕共享；
- 发版前同步 `CHANGELOG.md`、`AUDIT-MATRIX.md` 和 `VALIDATION-TODO.md`。

## 10. 最终验收门槛

在对外声称“达到或超过腾讯会议/UU远程”之前，必须满足：

- 至少 4 台真实 Android 设备、至少 2 种 ROM 完成测试；
- P2P、TURN、Wi-Fi、5G、弱网、切网全部有读数；
- Soul2Soul 与基准工具使用同一设备、同一网络、同一素材；
- 视频、语音、控制、温升和电量都有 P50/P95；
- 任何关键指标差于基准的场景都写出原因和产品边界；
- V-01、V-02、V-04、V-05 等相关真机格子不再用模拟器 PASS 替代；
- T0–T3 全绿，T4 不是 SKIP；
- 旧客户端、Android 7、MIUI、HyperOS 和 Android 14+ 的回退路径都已验证；
- 线上有可关闭新策略的开关；
- 发布说明不使用“理论上”“应该”“看起来没问题”作为验证结论。

## 11. 推荐的实施顺序

最稳妥的顺序不是先上 SFU 或盲目加码率，而是：

1. 先建立当前版本和竞品基线；
2. 再解决硬件编码器选择和指标可见性；
3. 再解决 Android 14+ 动态缩放；
4. 再做快降慢升的自适应和音频优先；
5. 再做 TURN 多节点和远程控制闭环；
6. 最后做热管理、灰度和自动回滚；
7. 用同条件 A/B 结果决定是否真的可以写“达到/超过”。

只要其中任一环没有真机证据，就把它保留为 `⬜`，不要用代码复杂度替代用户实际感受到的质量。
