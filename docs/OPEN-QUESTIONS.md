   ④ **新采到一种比 pong 更快的死法（10-17 22:03–22:28，米15=0.2.55 待机中，无人操作）**：`registered` 之后 **2.2s / 8.2s / 8.2s / 9.3s / 12.2s / 12.6s** 就 `[ws] close code=1006`（不是 30s pong 看门狗，服务器没那么快），每次死亡都向对端广播一次 `peer.gone`；重连节奏约 **7–9 分钟一次**（21:13、22:03、22:10、22:20、22:28），像 Doze 维护窗口放出来的短连接。含义：**只要会话期间出现同样的抖动，`peer.gone` 就会在 ICE 还 CONNECTED 时把会话拆掉**——这是"秒断"里唯一纯客户端就能治的一路（收到 `peer.gone` 先探 ICE 存活再拆，见 AUDIT-MATRIX §1 该行），而 `peer_signal` 探针正是为它准备的。读法警示：米15 现在还是 0.2.55，它这一侧没有 `signaling_up downMs=`，所以只能看到"socket 死了"看不到"死了多久/为什么"，**先把它升到 0.2.56 再复现**才有客户端差分。另：生产日志里 22:10:48 出现过第三台 `316c415a…`（code=54，`paired=false`，疑似本机 Mi5 开发机串台），复现读日志时别把它当成当事人的手机。
   ④ 的后续采样（10-18 07:11:50，仍是米15=0.2.55 待机、无人操作）：`registered` → **3.2 秒**后 `close code=1006 aliveFor=3272ms` + 广播 `peer.gone`，与 10-17 那批 2.2–12.6s 同签名。**0.2.57 已发布**（三处 sha256 一致 `a6f99317…`：本地 dist / 远端 `soul2soul-latest.apk` / `version.json`），米10 已 `adb install -r` 到 code=57 且 `registered.paired=true`（同签名覆盖安装，配对 token 未丢）；米15 侧仍停在 code=55——它只有打开 App 才会拿到更新，复现的硬门在这一点上。
   **10-17 生产日志已把「锁屏断」的自因抓到实锤**（0.2.55 时代，米10=`106db351` 作被控端）：`[18:02:00.171] [diag.event] role=sharer event=screen_off ice=CONNECTED detail=timeoutMs_15000` → 整 15 秒后 `[18:02:15.220] [diag.session] role=sharer reason=screen_off_timeout ice=CONNECTED liveMs=1134232 fg=false screenOn=false app=0.2.55`——一通 18 分 54 秒、拆线瞬间 ICE 还 CONNECTED 的会话，是被我们自己的 `stopSession(sendBye=true)` 结束的，不是网络、不是 ROM 拆采集；观看端那侧只留下一条 `reason=remote_bye`。同批另一条 `17:45:41 screen_off → 17:45:43 screen_on detail=rescued` 是反证：她 1.6 秒就解锁，会话才活下来。所以"聊着聊着一锁屏就断"在 0.2.55 上已有确定解（v0.2.56 删看门狗）。**但 0.2.56 的锁屏保活一次都没采到**——米10 20:50:47 才升到 code=56，此后到 22:03 服务器再没有通话；米15 仍是 code=55（`update=true`）。这条实锤只证明旧语义有害，**不能当成新语义已验证**，复现仍按上一条口径走。

   **10-18 对生产全量日志（4332 行，含 17:10 重启后 390 行带时间戳的仪器化窗口）复盘，三条把读数口径改掉的实锤**：
   ① **pong 超时不是主死因**：40 次 `[ws] close` 全是 `code=1006`，其中只有 **9 次**前面有 `pong 超时 terminate`，**31 次是裸 1006**（链路自己断的，服务器只是目击者）。上面预登记的分诊①覆盖面只有 22%，**服务端调 pong 宽限期治不到大头**，剩下的仍是「客户端对 `peer.gone` 先探 ICE」+ 重连退避这两条。同窗口 26 次死亡广播了 `peer.gone`（空闲 14 小时里就有 26 声"对方离线"），这是 F 的量级参照。
   ② **0.2.55 的 `video_stall` 已能判定为假告警，不用等真机**：一场会话内 5 条 stall 的 `rttMs=11/29/59/84/126`、`path=srflx-_srflx`、`ice=CONNECTED`——RTT 11ms 时报"黑屏"不可能是网络；`18:01:00.405` 那条就在 `18:01:00.245 surface_created` 之后 **160ms**，是观看端自己 surface 刚重建、零帧 streak 没清。0.2.57 的门控（`localRenderPaused` 清零 + `resumedSurfaceAtMs`→`video_resumed`）正对这一形态。
   ③ **`diag.session` 的 `liveMs`/`setupMs` 在"ICE 闪断后结束"的会话上是坏读数**：`18:02:15.790 role=viewer reason=remote_bye setupMs=1135965 liveMs=0` 把 18.9 分钟的会话报成"握手 18.9 分钟·live 0 秒"。根因是 `reportSessionEnd()` 用同一个 `connectedSinceMs` 既当"曾经连通"又当"连通起点"，而 DISCONNECTED/FAILED 分支会把它清 0（`WebRtcClient.kt:1217-1228`）——**恰恰是最该看的那类会话读数被污染**，复现前应当先修这个判据（拆成 sticky 的首次连通时刻），否则读到的 liveMs=0 会被误当成"从没通流"。

    - 四个结构性盲点不是"多打几行"能补的：①媒体走 P2P，服务器永远看不见，只有客户端自报；②`sendDiag` 只在信令活着时发得出，恰好瞎在断连那一瞬；③服务器广播 `peer.gone` 时不知道对方 ICE 实况（0.2.57 的 `peer_signal` 探针补的就是这条）；④`sessionMs` 只在收到 offer 的一端有值，观看端恒为 `-1`，会话期断连在服务器日志上分不清角色。

## C. 我替你做的技术决定（可否决，默认执行）

| # | 决定 | 理由 / 影响 |
|---|---|---|
| C1 | 信令服务器用 Node.js + `ws`，JSON 协议 | 服务器上零依赖部署；协议文档化在 SPEC §2，以后想换 Go/Java 重写也只需对齐协议 |
| C2 | TURN 用 coturn（优先 Docker，没有 Docker 就 apt 装） | 自建 WebRTC 的标配兜底，国内移动网络 P2P 成功率低 |
| C3 | libwebrtc 用预编译 AAR `io.getstream:stream-webrtc-android:1.1.1` | 自编译 libwebrtc 需要 100GB+ 磁盘和数小时，不值；API 就是官方 `org.webrtc.*` |
| C4 | minSdk 29（Android 10） | 两台目标机都远高于此，砍掉一堆旧系统兼容代码 |
| C5 | UI 用经典 View 而不是 Compose | 悬浮窗标注层必须是 View；全 App 统一技术，骨架期最不容易踩坑 |
| C6 | 无账号体系：deviceId(UUID) + 6 位配对码 | 恋人场景够了，省掉注册登录和短信费用 |
| C7 | 在线待命 = 常驻前台服务（低优先级通知） | 不接厂商推送前的唯一可靠方案；需要你俩手动开白名单（App 内有引导） |
| C8 | v0 信令走明文 `ws://IP`，v1 升 `wss` | 家庭场景风险可控；有域名后 30 分钟能升级 |
| C9 | TURN 凭证 = HMAC 时限凭证（1 小时有效） | 静态密钥不泄露的前提下，凭证被截获也只有 1 小时窗口 |
| C10 | 配对关系存服务器 `data/pairings.json` | 两人量级不需要数据库；文件备份即可 |
| C11 | 屏幕采集 720p@30 起步，长边≤1280 | 流量/发热/画质平衡点；libwebrtc 码率自适应兜底 |
| C12 | 标注走 WebRTC DataChannel（不走信令） | 端到端延迟最低，不经过服务器 |
