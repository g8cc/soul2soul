# 稳定性审计（2026-10-09，第一批）

## 范围与边界

阅读了信令客户端/常驻服务、会话路由、WebRTC 建立与释放、屏幕共享/悬浮层、留言存储/语音传输和服务端协议处理的主要路径。本轮不是全部源码或全部运行场景的完整验证，也未测量 CPU、内存、耗电或端到端时延。

服务器按仓库约定只审计，未修改、部署或读取线上数据；后续服务器修复及部署需用户明确确认。未跟踪的 `data/` 保持不动。

## 已复现并修复

1. 留言箱含非 JSON 对象时，`optJSONObject` 返回 null，但 `Msg.fromJson` 参数非空，调用点抛异常。PresenceService 的 collect 协程会退出，后续来电/留言分发处理可能停止。解析入口现在接受 null 并跳过，混合数组中的后续有效条目仍可解析。
2. SignalingClient 未实现 `onClosing`，OkHttp 默认回调不回应关闭帧，远端关闭无法由该回调及时完成握手，延迟后续关闭通知和重连。现在回应关闭握手；旧连接仍受原有 onClosed/onFailure 身份检查保护。单测验证回送关闭帧，网络端到端重连时间仍需实测。
3. InboxStore 批量入库先过滤再写入，同一批次内重复 ID 会覆盖首条，与单条入库规则矛盾。改为逐条判断后插入，保留首条，同时去掉临时过滤列表，避免一次额外遍历和分配。未做性能基准，不宣称整体性能提升百分比。

每个问题均有先失败后修复的 JVM 回归用例。

## 服务端待确认修复

以下是源码可见风险，尚未加入复现测试或修改；不应视为已完成漏洞验证：

- 语音下载 `fs.stat` 后 `createReadStream(...).pipe(res)` 缺少流错误处理，文件在两步之间被已读删除或清扫时可能触发未处理错误。
- 空语音上传在 end 回调直接返回，未完成 HTTP 响应；超限路径先销毁请求再写 413，客户端可能只收到连接重置。
- 语音上传缺少文件归属/待提交登记；被拒消息的文件删除路径应先验证标识符、上传所有者及引用状态；未提交上传也缺少孤儿回收。
- 配对码随机生成未检查已占用码，碰撞会覆盖另一设备的有效码。
- 同步持久化位于事件循环，配对/留言写盘失败缺少完整错误恢复，可能阻塞信令或使进程退出。

建议下一批在临时数据目录内补协议与文件竞态测试，先处理流错误、文件归属及落盘失败，再考虑异步持久化；不能简单改成异步写入而失去顺序和原子性。

## 后续真机/专项检查

- 两端反复建立/结束通话，观察 WebRTC native 对象、线程和内存是否回落；close 与 dispose 的所有权必须结合当前依赖实现核实，不宜盲改。
- 弱网、服务器主动关闭、Wi-Fi/蜂窝切换和后台唤醒，验证信令重连和 ICE 恢复。
- 留言上传期间退出页面、录音 stop 抛异常、并发下载同一语音，验证生命周期和缓存完整性。
- SharedFlow 使用 DROP_OLDEST，512 条缓冲不是可靠投递保证；需要压测后设计控制消息可靠路径，不能直接启用 replay 以免旧会话信令串入新会话。
- 手势、笔迹、授权及厂商系统表现未做真机验证，不声称手感或端到端稳定性已通过。
